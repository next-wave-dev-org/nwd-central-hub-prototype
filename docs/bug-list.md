# Bug List

A running log of known application-code bugs found during development and review, kept so future bug-hunting sessions don't rediscover the same issues from scratch. This is not a replacement for GitHub issues — open one for anything being actively worked.

Schema- and RLS-level design gaps (missing columns, unenforced constraints, tables not yet built) are tracked separately in the "Known Gaps" table in [`database-schema.md`](./database-schema.md) — not duplicated here.

## Open

| Severity | File | Bug |
|---|---|---|
| Low | Various | A number of pages historically didn't check `.error` on Supabase client calls, so a blocked/failed query (e.g. an RLS policy gap) silently rendered as an empty state instead of a visible error, making root causes hard to find. Fixed so far in `contractor/page.tsx`, `admin/requests/page.tsx`, `client/projects/page.tsx` (2026-07-15) and `admin/projects/page.tsx` (2026-09-07, #96) — the rest of the codebase still hasn't been swept for the same pattern. |
| Low | Site-wide (`app/change-password/page.tsx`, `app/login/client/proposals/new/page.tsx`, `app/login/admin/proposals/page.tsx`, and likely others) | Native `<button>` elements don't get a pointer cursor on hover unless explicitly styled with `cursor-pointer` (unlike `<a>`/`Link`, which are pointer by default). Fixed for the contractor-workflow pages (`contractor/page.tsx`, `admin/requests/page.tsx`, `client/projects/page.tsx`) on 2026-07-15 and `app/login/page.tsx` on 2026-07-16; worth a dedicated pass to fix the rest. |
| Low | [`app/login/admin/users/page.tsx`](../app/login/admin/users/page.tsx) | Page-reset/load logic runs as three separate `useEffect`s that call setState synchronously in the effect body — `loadUsers()` on mount, `setPage(0)` on search/sort change, `setPage(0)` on page-size change — flagged by the `react-hooks/set-state-in-effect` rule for triggering cascading renders. No visible symptom today since none of these feed back into their own dependencies, but should be derived state or event-handler resets instead of effects. |
| Low | [`docs/database-schema.md`](./database-schema.md) | The "Tables Overview" and the `proposal_requests` table section still mark `proposal_requests` as "❌ Not Built — pending #40", and `project_messages` similarly. `proposal_requests` is actually built and in active use (`admin/requests/page.tsx`, `client/projects/page.tsx`, confirmed against `docs/schema.sql`) — only `project_messages` is genuinely unbuilt. Found while updating this doc for the admin-initiated project creation issue (2026-07-16); left as-is since fixing it is a separate doc-accuracy pass, not part of that issue's scope. |
| Medium | [`app/change-password/page.tsx`](../app/change-password/page.tsx) | After a successful password change, the success message displays correctly but the user is bounced right back to `/change-password` instead of reaching their dashboard. Likely cause: `handlePasswordUpdate` calls `supabase.auth.updateUser({ password })` (which fires a `USER_UPDATED` auth event) and only afterward writes `is_temporary_password: false` to `profiles` — if `AuthProvider`'s `onAuthStateChange`-triggered `loadProfile()` refetches in the gap between those two calls, its context snapshot still has `is_temporary_password: true`, and nothing re-fetches it after. The subsequent `router.push('/')` then hits `RouteGuard` on the destination page with stale context, which force-redirects back to `/change-password`. Needs either a profile-refresh hook on `AuthProvider` called after the `profiles` update, or reordering the two writes so the flag is already `false` before `updateUser` fires the event. |
| Low (enhancement) | [`app/login/admin/users/page.tsx`](../app/login/admin/users/page.tsx) | User management only supports one-at-a-time actions (edit/reset/delete per row) — no row checkboxes, no "select all," and no bulk action bar, so an admin cannot mass-delete or mass-update users. Reported during dev review (2026-07-22); scope a bulk-selection UI + a `deleteUsers(ids: string[])` server action alongside the existing single-user `deleteUser` in `actions.ts`. |

## Resolved

| Date | Issue | Fix |
|---|---|---|
| 2026-09-07 | `app/login/admin/projects/page.tsx` checked `if (!error)` on its Supabase fetch but never surfaced a failure — a blocked/failed query rendered as "No active projects" instead of an error, unlike its sibling `client/projects/page.tsx`. (Issue #96) | Added an `error` state plus the shared rose error banner (same markup as `client/projects` / `admin/requests`); the fetch now calls `setError(error.message)` in the failure branch. |
| 2026-09-07 | `app/login/contractor/page.tsx` — `fetchData` was called inside `useEffect` above its own declaration, working only via function-declaration hoisting; failed the `react-hooks` "cannot access before declared" rule and `exhaustive-deps` flagged the missing dependency. Also called `setLoading(true)`/`setError(null)` synchronously at the top of the loader, the same `react-hooks/set-state-in-effect` shape flagged elsewhere. (Issue #96) | Moved the loader inside the effect as a local `const fetchData = async () => {…}` with a `cancelled` guard, keyed on `[profile]`. `loading` now initializes to `true` so the synchronous `setLoading(true)` prefix is gone; state is only set after the `await`. Also typed the previously-`any` row callback as `{ project_id: string }`. |
| 2026-07-22 | `app/unauthorized/page.tsx`'s only action was a "Return home" link to `/`. For a user with a valid `profiles` row but the wrong role this correctly bounces them to their own dashboard, but for an authenticated user with **no** `profiles` row (e.g. an OAuth sign-in that created a new `auth.users` entry instead of auto-linking to an existing account — see "OAuth Sign-In & Account Linking" in `architecture.md`) it's an infinite loop: `proxy.ts` finds no profile at `/`, falls through to the catch-all `requiresAuth` check, and redirects back to `/unauthorized`. Typing `/login` manually hits the same trap. Found while testing #84/PR #104 (GitHub/LinkedIn sign-in landed on a new profile-less user). | Added a "Sign out" action to `/unauthorized` (`supabase.auth.signOut()` + redirect to `/login`, matching the existing logout pattern in `components/UserMenu.tsx`) as an escape hatch independent of the profile-lookup outcome. |
| 2026-07-20 | The old role-based global-nav component (formerly `components/Navbar.tsx`) had a `fetchRole()` effect querying `profiles.role` into dead `role` state the JSX never read, plus a shadowed `useAuth()` `profile` — a redundant Supabase round-trip and a latent bug magnet. | Resolved by deleting that component outright: it was unused once all pages moved to the shared header. The shared header (built this session as `NWDHeader.tsx`) was then **renamed to `components/Navbar.tsx`** and is now the single navbar component used across all 14 pages. |
| 2026-07-20 | `app/login/admin/projects/page.tsx`, `app/login/client/projects/page.tsx`, and `app/login/admin/projects/new/page.tsx` were missing `UserMenu` in their header — the only way off those pages was the browser back button or the "Back" link, with no way to log out or reach Profile/Settings. Also, the single-segment breadcrumb on the three root dashboard pages (`admin/page.tsx`, `client/page.tsx`, `contractor/page.tsx`) rendered gray instead of teal, contradicting `docs/style.md`'s own documented convention ("current page: teal, non-clickable"). | Extracted the header markup duplicated across 14 pages into `components/Navbar.tsx` (issue #86) — it always renders `UserMenu` and always renders the last breadcrumb segment in teal, so both inconsistencies are fixed by construction for every page migrated to it. Migrated: `admin/page`, `admin/projects/page`, `admin/projects/new/page`, `admin/proposals/page`, `admin/requests/page`, `admin/users/page`, `client/page`, `client/projects/page`, `client/proposals/page`, `client/proposals/new/page`, `contractor/page`, `projects/[id]/page`, `profile/page`, `settings/page`. |
| 2026-07-20 | Per-page header containers used inconsistent `max-w-*` values (`max-w-2xl` on dashboard-root pages, `max-w-3xl` on `admin/requests`, `max-w-5xl` elsewhere), so the logo visibly jumped horizontally when navigating between pages. Separately, the "NextWaveDev" wordmark had no mobile treatment, crowding the breadcrumb trail on narrow viewports. On top of that, the browser scrollbar appearing only on pages tall enough to scroll narrowed those pages by its width, shifting the centered header relative to non-scrolling pages. | Fixed via `Navbar` + `app/globals.css`: (1) `html { scrollbar-gutter: stable }` always reserves the scrollbar gutter, so page width is constant whether a page scrolls or not — no shift. (2) The header uses two nested containers — an outer `w-[90%] mx-auto` carrying the `border-b` divider, and an inner `max-w-5xl mx-auto` holding the content — so the divider spans 90% while the logo/menu stay at a consistent capped position. The divider lives on the centered container rather than a full-bleed `<header>` because the reserved scrollbar gutter can't be painted into, so a full-bleed border would leave a gap at the right edge. (3) The "NextWaveDev" wordmark hides below the `sm` breakpoint so the breadcrumb trail runs directly off the logo on mobile. |
